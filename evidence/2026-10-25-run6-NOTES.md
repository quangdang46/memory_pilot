# Run 6 — harness notes (read before using its score)

Run 6 is the first run against the fixed daemon. Two of its five labels are
not valid tests, and the score must be read accordingly.

## probe-children: invalid label

The probe spawns 20 `sleep` children to model subprocess accumulation. They
are correctly parented (verified: `ppid` = the probe), but each `sleep` holds
~0 MB footprint, so the group's total growth is 0 MB and it can never clear
`MinGroupGrowthBytes`. Measured: `probe-children growth=0MB procs=1` in the
window, while 20 children existed.

Two separate facts:
- the probe is a bad model (a sleeping child allocates nothing);
- the daemon reported `procs=1` for a group that had 21 processes — either
  the zero-footprint children were filtered out of the series, or grouping
  did not attach them. NOT diagnosed. Do not claim either way.

The label `subprocess_accumulation` is therefore untested, not passed and not
failed.

## probe-plateau: label needs care

It allocates 14 MB x 8 ticks then holds. Its growth in later windows is 0, so
`MinGroupGrowthBytes` filters it out of classification entirely (the same
filtering behaviour diagnosed in WHY-IT-DOES-NOT-WORK §3). A correct cache
verdict would require judging a group that is no longer growing. That path is
still not fixed. Its absence from the score is expected, not news.

## What run 6 does test

- `probe-leak` → `leak_suspicion` at 1200 s (measured, matches label)
- `probe-workload` → `workload_growth` 0.89-0.90 (matches label)
- `probe-sawtooth` → misclassified as `leak_suspicion` because release was
  not accumulated across window resets; fixed after this run
  (`8bc2aaa`), needs a re-run to confirm
- the same-run contrast that motivated all of this: Chrome and node, which
  were labelled `leak_suspicion` four windows running before the fix, are now
  `cache_or_retrievable` with release as their stated basis

## Not tested by run 6

- subprocess accumulation (bad probe)
- cache verdicts for a group that stopped growing (still filtered out)
