# Defects 10–12 — found by re-running the experiment, not by reading code

Three defects, all from the same run16 window (11:50:25), all invisible in the
run8 evidence that was previously called proof.

## 10 — a new group inherits a dead group's evidence

`probe-leak`, 306 s old, reported `window 884s`; `probe-children` reported
`1049s`. Both numbers came from run12 groups recorded an hour earlier:
`history` is keyed by anchor name and was only evicted at >4096 entries.

`DurationS` gates the leak branch, so a brand-new process could be called a
leak on its first appearance — the exact warning the owner asked never to see
again.

Fixed by `retireGoneGroups` (120 s after the group's last live member).
Test: `TestHistoryRetiredWhenGroupDisappears`.
Detail: `2026-10-25-history-inheritance.md`.

## 11 — 1 MB of churn called a cycling cache

```
11:50:25 probe-children cache_or_retrievable
         "released 1 MB while growing 0 MB — cycling, not accumulating"
```

The cycling branch required both sides non-zero but not *material*. One
megabyte of churn over twenty minutes is noise, and the "cache" verdict
suppressed the process accumulation that was actually happening.

Fixed: `MinCyclingBytes = 32 MB`. Both directions tested —
`TestNegligibleChurnIsNotCycling` and `TestRealCyclingStillDetected`.

## 12 — a subprocess that starts holding memory is not counted as growth

Measured directly, while run16 was live:

```
probe-children group, footprint of every process:
  9332 3.4 MB | 10005 15.6 | 10371 15.7 | 13014 15.3 | 13990 15.5
  14748 15.3 | 18917 15.4 | 22295 15.4 | 23223 15.6
  group total: 127.2 MB
daemon window: growth 5 MB
```

The first sighting of a process was used as a baseline with no delta, so a
child spawned at 15 MB contributed nothing. `subprocess_accumulation` needs
growth, so the bucket could not fire on its own signature.

Fixed: a process whose start time is after the first snapshot contributes its
full footprint as growth. A process that predates observation is baseline.

Both halves are tested:
- `TestNewProcessArrivalCountsAsGrowth`
- `TestPreexistingProcessesAreBaseline` — without it, the daemon's own startup
  read as ~20 GB of growth, because the machine was already full of processes.

## A latent bug the fix exposed

Making new processes flow through the history path revealed that
`seriesForLocked` divided by a span of microseconds for a group first seen on
the tick being read: `5.9e13 B/s` from two ordinary samples. Guarded at
`span >= 1`.

## What this says about run8

run8 was not wrong, but it was not enough. It exercised the shapes and the
thresholds; it did not exercise a daemon that had already seen those group
names, or a group growing by *arrival* rather than by *allocation*. The
harness now checks both before a run counts:

- a probe with no group of its own name after the first window is a failure;
- a claimed evidence window longer than the run's own age is a failure.

## 13 — the mirror of 12: a process that exits releases nothing

Fixing 12 created the opposite imbalance. A child spawned at full size counted
as growth; its exit counted as zero, so the accounting only ran one way.
Measured on this machine, on every window of the previous build:

```
wezterm-gui  632 MB growth, 14 processes   (11:59:52)
wezterm-gui  787 MB growth, 14 processes   (11:59:52, prior)
node         684 MB growth, 27 processes   (12:07:12)
```

A terminal that runs a compiler per build accumulated its children's peak
footprint forever while holding none of it.

Fixed by charging `prevBytes` to the group's release when a dead series is
swept. The series now remembers its group, because a dead process is absent
from the snapshot and its ancestry can no longer be walked at sweep time.

Test: `TestExitedProcessReleasesItsMemory`.

## A harness defect that this exposed

The new gate in `verify_inputs.py` failed a good run18 on run17's verdicts: it
read the whole ledger, and probe names are reused between runs. Scoped to rows
at or after `started.txt`, like `score.py` already was. Worth writing down
because the gate was right about the *shape* of the failure and wrong about
which run it belonged to — and a gate that cries wolf is worse than none.

## Where the score stands

run17 was discarded: it ran on a binary that carried 12 but not 13, so its
windows still showed wezterm-gui accumulating short-lived children. run18 is
the first run on the daemon carrying all thirteen fixes. Its result is recorded
in `2026-10-25-run18/`; nothing in this file claims a score.
