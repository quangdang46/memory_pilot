# run12 — discarded: the harness fed the daemon the wrong lineage

**Result: not evidence.** No verdicts from run12 are scored.

## What happened

All five probes were attributed to one group, `wezterm-gui`, instead of being
grouped separately. The first two windows showed only:

```
11:30:15  probe-children  unknown 0
11:35:20  probe-children  unknown 0
```

and the only probe-named group in either window was `probe-children`.

## Why

Memory Pilot groups a process under its **nearest anchor ancestor** (§4.1), and
a terminal is deliberately an anchor — that is what makes "everything this
wezterm session started" one row in the report.

run12 was started the same way run8 was: `nohup ./start_run.sh run12` from the
Claude Code shell. This time the shell's ancestry had not been severed:

```
probe-leak (20106)
  → python3 (20105)
  → /bin/sh (20101)
  → <Claude Code shell>
  → wezterm-gui
```

So `wezterm-gui` *was* the nearest anchor ancestor, and grouping the probes into
one terminal group was correct behaviour, not a defect. run8 only worked because
its parent chain happened to end before reaching the terminal.

Attribution rows confirm the merge rather than a lost process:

```
wezterm-gui  largest_pid=20106  procs=21  growth=914MB  release=536MB
```

`largest_pid` is a probe pid, inside the terminal group.

## The harness defect

An experiment that measures per-probe verdicts must guarantee the probes are
their own group. The launcher did not assert that; nothing in the run checked
grouping before the 30 minutes were spent. `verify_inputs.py` checks that the
right processes are running with the right footprint and parentage — it never
checked that the *daemon* sees them as separate groups. That is the gap.

## Fix

`detach_run.py` double-forks so the probes' ancestry ends at launchd:

```
probe-leak (47459)
  → python3 (47458)
  → /bin/sh (47454)   ppid=1
```

The launcher itself stays alive as the parent, so `probe-children` keeps its
own children and subprocess accumulation stays testable. Verified on run15
before spending the window:

```
probe-children: pid=47463 ppid=47458 footprint=3MB children=1
probe-leak:     pid=47459 ppid=47458 footprint=16MB children=0
probe-plateau:  pid=47460 ppid=47458 footprint=32MB children=0
probe-sawtooth: pid=47462 ppid=47458 footprint=24MB children=0
probe-workload: pid=47461 ppid=47458 footprint=15MB children=0
```

Two earlier attempts to detach failed and were discarded: `launchctl submit`
killed the job after ~10s (exit 1) on this machine, twice, with the same
plist and a direct `/bin/sh` invocation that works in a clean environment.
Double-fork avoids depending on that behaviour.

## Note on the product

Nothing here says the classifier got better or worse. The run that carries
evidence remains run8 (4/5, with the sawtooth miss diagnosed as a bad label).
Re-run as run15 after this fix.
